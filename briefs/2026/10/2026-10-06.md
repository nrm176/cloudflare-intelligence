# Cloudflare Intelligence Brief — 2026-10-06

## エグゼクティブサマリー

前回Brief以降（10月5日〜10月6日朝）に、Cloudflareから新しい大型Developer Platform製品の発表は確認できませんでした。10月5日のBirthday Week総括は46件の既発表を整理したもので、AI Search GA、K2、Basin GA、KV Instant、Clef、Cloudflare Traces、AI Gateway Web Search APIなどは前回Briefで扱った内容の再掲です。

今回の実質的な新規シグナルとして重要なのは、WAFドキュメントで明確化された **Workers subrequestの発信元zoneを識別して制御する `cf.worker.upstream_zone`** です。マルチテナント、複数zone、Agent/Worker間通信をCloudflare上で構築する企業にとって、Worker-to-Worker通信を「内部だから信頼する」のではなく、WAF境界で明示的に制御できる実務的なセキュリティ機能です。

## 1. 何が変わったか

### Workers subrequestをWAFで発信元zone単位に制御

**事実:** Cloudflareは2026年10月5日更新のWAFドキュメントで、`cf.worker.upstream_zone` フィールドを使ってWorkers subrequestを生成したzoneを識別し、Custom Rulesでblock/allowできる方法を明示しました。特定zoneからのsubrequestを拒否することも、自社zone以外のWorker subrequestを一括拒否することもできます。

またCloudflareは、`CF-Worker` request headerはWAF rule評価後に付与されるため、WAF条件には使用せず `cf.worker.upstream_zone` を使うよう注意しています。

**分析:** Cloudflareを複数アプリ/複数zoneの共通基盤として使う場合、Worker間通信そのものが新しいeast-west trust boundaryになります。このフィールドは、アプリケーションコードだけに認可を任せずedge/WAFでも送信元を制限するdefense-in-depthに使えます。

## 2. なぜ重要か

Agentや自動化Workerが増えるほど、サービス間requestは人間のブラウザtrafficより増加します。そこで「Cloudflare Workerから来たrequestだから安全」という暗黙のtrustは危険です。

推奨する考え方は、

**Internet / Worker / Agent → WAF origin-zone policy → Access/service identity → application authorization → origin**

という多層化です。

`cf.worker.upstream_zone` はidentityそのものではないためAccess service tokenやmTLS等の代替にはなりませんが、不要なzoneからのWorker trafficを入口で落とすpre-filterとして有効です。

## 3. 具体的なユースケース／シナリオ

- 社内APIを呼べるWorkerを自社管理zoneに限定する。
- 複数顧客zoneを扱うSaaSで、意図しないcross-zone Worker requestを遮断する。
- Agentが複数Workersをtoolとして呼ぶ構成で、許可されたzoneだけをWAFで通す。
- Cloudflare上のpublic endpointに対して、外部ユーザーtrafficは許可しつつ他社Workerからの自動subrequestだけを拒否する。

## 4. 技術的な示唆・統合パターン

WAF ruleだけを認証機構として扱わず、`cf.worker.upstream_zone` はnetwork/application perimeterの補助信号として利用するのが適切です。

例えば、WAFでunknown Worker zonesを拒否し、その後Cloudflare Accessまたはservice tokenでworkload identityを確認し、最終的にapplication側RBACで操作権限を判定する三段構成が堅牢です。

また、Worker/Agentの数が増える組織では、zone間依存関係をinventory化し、このWAF policyをIaCで管理する価値があります。

## 5. 見落とされがちだが有用な機能

### `cf.worker.upstream_zone`

**何か:** Workers subrequestを生成したCloudflare zoneをWAF Custom Rulesから参照できるフィールドです。

**なぜ見落とされやすいか:** Birthday Weekの大型発表ではなく、WAFのuse-case documentationとして更新されているためです。

**解決する問題:** Worker-to-Worker trafficの発信元を区別できず、外部zoneのWorkerから自社endpointへ自動requestされるケースをedgeで制御しにくい問題を解消します。

**誰に有用か:** Cloudflare platform team、Security Engineering、Zero Trust/IAM担当、複数zoneを運用するSaaSチーム。

**利用例:** 自社の `corp.example` zoneから生成されたWorker subrequestだけを許可し、それ以外のWorker-originated requestをWAFでblockする。一方、通常の直接visitor trafficは空文字判定を利用して許可する。
