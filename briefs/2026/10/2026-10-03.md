# Cloudflare Intelligence Brief — 2026-10-03

> 初回テスト実行のため、通常の差分監視より広く、2026-09-01〜2026-10-03 の主要更新をバックフィルしています。一次情報で確認できる事実と、それに基づく分析・示唆を分けて記載します。

## エグゼクティブサマリー

今回の更新群から見える大きな方向性は、Cloudflare が単なる CDN / Zero Trust / edge runtime の集合から、**AI Agent、データ、イベント、セキュリティ、MCP、開発環境を同じグローバル基盤でつなぐ「実行・統制プレーン」**へ広がっていることです。

特に企業アーキテクチャでは、次の3点が重要です。

1. **AI Gateway が単なる LLM proxy ではなく、web search、BYOK、observability、billing、access control をまとめる AI control plane に近づいている。**
2. **Cloudflare One / Access が MCP server portal、DLP、service token、Logpush を通じて Agent / MCP の統制ポイントになっている。**
3. **Developer Platform に K2、Basin、Worker Previews、細粒度 RBAC、強化された tracing が加わり、Cloudflare 単独で構成できる業務アプリ・Agent 基盤の範囲が広がっている。**

## 1. 何が変わったか

### 1.1 AI Gateway に Web Search API

**事実:** 10月2日、Cloudflare は AI Gateway 経由の Web Search API を発表しました。Ceramic.ai、Exa、Linkup を初期プロバイダーとし、REST API および Workers binding から利用できます。AI Gateway の通常の observability、billing、access control と統合され、BYOK も利用可能です。

**分析:** Agent が live web を扱うための search tool を各アプリで個別実装する必要が減ります。Cloudflare を AI Gateway として既に使っている場合、model inference と search を同じ control plane で監査・課金・制御できる点が実務的に大きいです。

### 1.2 AI Search が GA、multimodal / OCR に対応

**事実:** 10月1日、AI Search が GA になりました。Workers AI、Vectorize、R2、Browser Run を組み合わせた managed retrieval pipeline として、native image embeddings、PDF OCR、10 MiB までのファイル、hybrid/vector/full-text search を提供します。課金開始は11月1日予定です。

**分析:** 小〜中規模の社内RAGでは、独自の ingestion / parsing / embedding / index / reranking パイプラインを持つ必要性がさらに低下します。特に図面、スクリーンショット、スキャンPDFを含む企業ナレッジとの相性が良くなっています。

### 1.3 Clef / Clef-flash — decision model と RL fine-tuning

**事実:** 10月1日、Cloudflare は Workers AI 上で Clef と Clef-flash を公開しました。自由文生成ではなく、schema に従った確率付き decision output を返すモデルで、Apache 2.0 で open source 化されています。Cloudflare は顧客データを使った RL fine-tuning サービスも開始しています。

**分析:** Agent のすべての判断を大規模 LLM に任せるのではなく、「分類・routing・escalation・policy decision」は小型 decision model に分離するアーキテクチャが現実的になります。低遅延・低コスト・typed output が必要なワークフローに向きます。

### 1.4 Cloudflare OS の managed deployment

**事実:** 10月1日、Cloudflare OS の fully managed deployment の waitlist が開始されました。Access policy、AI Gateway、社内 context / skill / systems を組み合わせ、GitHub repository 操作、Google Workspace、各種 document export などを Agent workspace から扱う方向が示されています。

**分析:** Cloudflare 自身が「社内 AI workspace」を product layer として持ち始めています。Workers + Access + AI Gateway + internal connectors を組み合わせた社内DX基盤を自社開発する際の reference architecture としても注目すべきです。

### 1.5 K2 — serverless event streams

**事実:** 10月1日、Cloudflare K2 が public beta で公開されました。R2 を基盤とした durable ordered log で、HTTP API または Worker binding からイベントを送信でき、consumer pool / pub-sub の双方を構成できます。Workers Paid 向けに beta 提供されています。

**分析:** これまで Cloudflare 中心の構成で Kafka 相当の durable stream が必要な場合は外部基盤を併用することが多かったですが、K2 により edge event → durable stream → Worker / Basin / external consumer という構成が自然になります。

### 1.6 Cloudflare Basin が GA

**事実:** Cloudflare Data Platform は Cloudflare Basin に改称され GA となりました。Basin Pipelines、Basin Catalog、Basin SQL を含み、Apache Iceberg + R2 を中心とした serverless analytics platform です。DuckDB、Spark、Snowflake など Iceberg 対応 engine からデータを扱えます。

**分析:** 「R2 に Parquet を置いて DuckDB 等から読む」設計を、より正式な lakehouse / Iceberg 構成へ段階的に拡張しやすくなります。Cloudflare の zero egress と open table format の組み合わせは、分析基盤の cloud lock-in を弱める方向に働きます。

### 1.7 cf — Agent 向け unified CLI

**事実:** 9月28日、Cloudflare は open beta の新 CLI `cf` を発表しました。Cloudflare API 全体をカバーすることを狙い、JSON-first output、command search / steering、TypeScript ベースの `cloudflare.config.ts`、Vite を軸にしています。

**分析:** Wrangler が Workers-centric だったのに対し、`cf` は「Agent が Cloudflare 全体を操作する interface」として設計されています。IaC / CI / coding agent と Cloudflare API の接点として今後重要になる可能性があります。

### 1.8 MCP server portals が GA

**事実:** 9月24日、Cloudflare One の MCP server portals が GA になりました。複数の承認済み MCP server を1つの endpoint にまとめ、Access による tool / prompt / resource activity logging、Gateway 経由の HTTP logging / DLP、service token、Logpush、session management などを提供します。private network 内 MCP server にも接続できます。

**分析:** MCP を企業利用する際に最も難しい「どの server を許可するか」「誰が何を呼んだか」「機密データを外に出していないか」を Cloudflare One で集中管理できる形になっています。

## 2. なぜ重要か — エンタープライズアーキテクチャ / 社内DX

Cloudflare の Developer Platform、Cloudflare One、AI Gateway の境界がかなり薄くなっています。

従来なら、Web application は Workers、network security は Zero Trust、AI は別 SaaS、event streaming は Kafka、analytics は別 cloud warehouse という分割が一般的でした。現在は、**Access → Worker → AI Gateway / Workers AI → K2 / R2 / Basin → observability** という形で、かなりの部分を Cloudflare 内で一貫して構築できます。

これは「Cloudflare だけを使うべき」という意味ではありません。むしろ重要なのは、Cloudflare が **edge execution + identity-aware access + AI control plane + open data layer** を一つのアーキテクチャ境界として提供し始めたことです。

## 3. 具体的なユースケース / シナリオ

- **社内 Agent gateway:** Entra ID → Cloudflare Access → MCP Portal → approved MCP servers。tool call を Gateway/DLP/Logpush で監査。
- **外部情報を使う Agent:** Worker / Agent → AI Gateway Web Search → model inference。search と inference を同じ gateway で observability / billing。
- **建築・不動産ナレッジ検索:** PDF、スキャン資料、図面画像を R2 / AI Search に取り込み、OCR + multimodal retrieval を利用。
- **イベント駆動 SFA / CRM:** Worker から K2 に業務イベントを発行し、複数 consumer が分析、通知、AI処理を独立実行。
- **Cloudflare-native analytics:** Logpush / application event → Basin Pipelines → Iceberg/R2 → Basin SQL または DuckDB。
- **Agent-driven infrastructure management:** coding agent が `cf` CLI / TypeScript config を使い、Cloudflare resource を検索・変更し、Preview で検証してから production deploy。

## 4. 技術的な示唆・統合パターン

### AI / Agent

```
User / System Event
    ↓
Cloudflare Access
    ↓
Worker / Agent
    ├─ AI Gateway → LLM / Web Search
    ├─ MCP Portal → Approved MCP Servers
    ├─ Browser Run
    └─ Workers AI / Clef
```

LLM は生成・reasoning、Clef は routing / classification / policy-like decision に分離する構成が考えられます。

### Data / Event

```
Worker / Device / Logpush
    ↓
K2
    ├─ Worker consumer
    ├─ External consumer
    └─ Basin Pipelines
           ↓
       R2 / Iceberg
           ↓
    Basin SQL / DuckDB / Spark
```

### Governance

MCP traffic は Portal に集約し、Access identity、Gateway DLP、service token、Logpush を組み合わせることで、人間と autonomous agent を同じ policy plane で扱えます。

## 5. 見落とされがちだが有用な機能

### 5.1 Worker Previews — branch ごとの隔離環境

**何か:** 各 Preview が独自の code、configuration、URL、observability を持ち、Durable Objects / Containers は Preview ごとに別 namespace / state が自動で用意されます。

**なぜ見落とされやすいか:** Workers の大規模な新サービス発表ではなく、9月22日の developer workflow 改善としてリリースされたためです。

**解決する問題:** Agent や開発者が複数 branch を並列で変更するとき、stateful resource を共有して production や他 branch を壊すリスクを減らします。

**誰に有用か:** Application team、Platform Engineering、coding-agent 導入チーム。

**利用例:** PRごとに Durable Object を含む isolated Preview を自動生成し、Agent が変更→E2E test→review URL共有まで実行する。

### 5.2 Worker 単位の細粒度 RBAC

**何か:** individual Worker に対し Metadata Read-Only、Content Read-Only、Editor、Admin の4 role を割り当てられます。API / Terraform からも設定可能です。

**なぜ見落とされやすいか:** Workers の permission model の変更であり、派手な product launch ではないためです。

**解決する問題:** Cloudflare account 全体の権限を Agent、CI/CD、外部チームに与える必要がなくなります。

**誰に有用か:** Security、Platform Engineering、複数開発チームを持つ企業。

**利用例:** deployment agent に対象 Worker の Editor だけを与え、他 Worker や account-wide resource への権限を与えない。

### 5.3 Workers VPC / Mesh / Tunnel replica の network log 識別

**何か:** Gateway network logs / Zero Trust Network Session Logs で Mesh traffic と Workers VPC traffic を区別でき、どの Tunnel / cloudflared replica が session を受けたかも確認できます。

**なぜ見落とされやすいか:** observability の小さな changelog 項目ですが、Agent / Worker から private network へ接続する構成では重要です。

**解決する問題:** 人間端末と autonomous Worker/Agent traffic が同じように見える問題を解消し、障害調査・監査を容易にします。

**誰に有用か:** Network/Security team、SRE、Agent platform team。

**利用例:** Worker VPC 経由で Azure SQL / private API にアクセスする Agent の通信を人間ユーザーの通信と分離して監視する。

### 5.4 R2 Data Access Logs

**何か:** R2 bucket の read / write / list / multipart / delete を Workers Observability に記録できます。S3 API、Cloudflare API、dashboard、Workers binding、public bucket access をカバーします。

**なぜ見落とされやすいか:** R2 自体の新機能ではなく、運用・監査機能として GA になったためです。

**解決する問題:** 「どの actor/interface が object を読んだ・変更したか」を bucket-level で調査しやすくなります。

**誰に有用か:** Security、Data platform、SRE。

**利用例:** AI ingestion pipeline が R2 のどの object を読み込んでいるか、異常な delete/list pattern がないかを Workers Observability で追跡する。

**注意:** Cloudflare は delivery を asynchronous / best-effort としており、完全な監査台帳として単独利用すべきではありません。

### 5.5 Workers tracing の RPC session spans / custom span API 強化

**何か:** Worker-to-Worker JavaScript RPC と Durable Objects を跨ぐ session / method call が trace に自動表示され、`startSpan()`、`getActiveSpan()`、`recordException()`、`setAttributes()` なども追加されています。

**なぜ見落とされやすいか:** observability API の incremental update ですが、分散 Workers architecture では実用価値が高いためです。

**解決する問題:** RPC boundary で trace が切れ、どの Worker / Durable Object が遅いか判断しづらい問題を改善します。

**誰に有用か:** SRE、backend engineer、platform team。

**利用例:** Agent orchestration Worker → domain Worker → Durable Object の chain を1 trace で追い、LLM tool latency と internal RPC latency を切り分ける。

### 5.6 Private MCP server を Portal から利用

**何か:** MCP Portal が Tunnel / Mesh / Cloudflare One connector を経由して private hostname / IP 上の MCP server に接続できます。

**なぜ見落とされやすいか:** MCP Portal GA の少し前に追加された個別機能で、Portal 本体の発表に埋もれやすいためです。

**解決する問題:** internal MCP server を public Internet に公開せずに ChatGPT / coding agent 等から安全に利用できます。

**誰に有用か:** Enterprise Architecture、Security、internal AI platform team。

**利用例:** 社内 Dataverse / ERP / SQL 用 MCP server を private network に置いたまま、Cloudflare Access の認証・監査を通して Agent に公開する。
